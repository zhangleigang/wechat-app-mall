# HDFS面试题：NameNode宕机的数据恢复过程是什么？

## 📋 面试问题

**面试官问**：如果NameNode宕机了，数据恢复过程是怎样的？

## ⚡ 快速回答（2-3分钟版本）

### 核心要点
1. **非HA环境**：手动重启NameNode，自动重放EditLog恢复元数据，等待DataNode块报告
2. **HA环境**：ZKFC自动检测故障，Standby NameNode自动切换为Active，几乎无数据丢失
3. **关键文件**：FsImage（元数据快照）+ EditLog（操作日志）是恢复的基础

### 一句话总结
NameNode宕机恢复分为非HA（手动重启+元数据重放）和HA（自动故障转移）两种模式，HA模式可实现秒级恢复。

## 📖 详细解析

### 1. NameNode核心数据

**元数据内容**：
- 文件系统命名空间（目录结构、文件属性）
- 文件与数据块的映射关系
- 数据块与DataNode的映射关系（内存中，启动时重建）

**持久化文件**：
- **FsImage**：某时刻元数据的完整快照
- **EditLog**：FsImage之后的所有写操作记录

### 2. 非HA环境恢复流程

**步骤1：问题诊断**
- 检查硬件、操作系统、网络等底层问题
- 确保FsImage和EditLog文件完整无损

**步骤2：启动恢复**
- 重启NameNode进程
- 自动加载最新FsImage到内存
- 重放EditLog中的所有操作，恢复到最新状态

**步骤3：重建块映射**
- NameNode进入安全模式（只读状态）
- 等待DataNode发送块报告
- 重建数据块到DataNode的映射关系

**步骤4：完整性检查**
- 运行hdfs fsck检查文件系统健康状况
- 自动复制副本不足的数据块
- 满足条件后自动退出安全模式

### 3. HA环境自动恢复

**架构组件**：
- **Active NameNode**：处理所有客户端请求
- **Standby NameNode**：热备状态，实时同步元数据
- **ZKFC**：故障检测和自动切换控制器
- **JournalNode集群**：共享EditLog存储

**自动恢复流程**：
1. **故障检测**：ZKFC检测到Active NameNode宕机
2. **Fencing操作**：确保旧Active节点完全下线
3. **自动切换**：Standby NameNode提升为新的Active
4. **服务恢复**：客户端自动连接新的Active节点

**恢复时间**：通常在30秒内完成，几乎无数据丢失

### 4. 数据安全保障

**元数据保护**：
- 多目录存储FsImage和EditLog
- Secondary NameNode定期合并检查点
- HA模式下的实时同步机制

**故障预防**：
- 定期备份元数据到集群外
- 监控NameNode内存和磁盘使用
- 建立完善的告警机制
