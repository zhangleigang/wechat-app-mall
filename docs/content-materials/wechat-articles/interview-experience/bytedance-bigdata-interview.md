### 技术问题回顾

#### 问题1：详细说明HDFS的读写流程，为什么要设计成这样？

**我的回答**：
HDFS采用主从架构，包括NameNode和DataNode。

**写流程**：
1. 客户端向NameNode请求创建文件
2. NameNode检查权限和文件是否存在
3. 客户端请求第一个数据块的DataNode列表
4. NameNode返回DataNode列表（按网络拓扑排序）
5. 客户端向第一个DataNode写入数据
6. DataNode之间建立pipeline进行数据复制

**读流程**：
1. 客户端向NameNode请求文件的数据块位置
2. NameNode返回数据块及其副本位置信息
3. 客户端选择最近的DataNode读取数据

**设计原因**：
- 分离元数据和数据存储，提高系统可扩展性
- 通过副本机制保证数据可靠性
- 数据本地性优化减少网络传输

**面试官追问**：如果NameNode宕机了怎么办？Secondary NameNode的作用是什么？

**我的回答**：
- NameNode宕机会导致整个集群不可用
- Secondary NameNode不是热备份，主要作用是定期合并fsimage和edits日志
- 生产环境通常使用NameNode HA方案，通过ZooKeeper实现主备切换

#### 问题2：为什么Spark比MapReduce快？具体快在哪里？

**我的回答**：
主要体现在以下几个方面：

1. **内存计算**：Spark将中间结果缓存在内存中，避免频繁的磁盘I/O
2. **DAG执行引擎**：Spark采用DAG执行计划，能够优化整个作业流程
3. **避免不必要的磁盘写入**：MapReduce每个阶段都要写磁盘，Spark可以在内存中完成多个操作
4. **更丰富的算子**：Spark提供更多高级算子，减少开发复杂度

**面试官追问**：什么场景下MapReduce比Spark更合适？

**我的回答**：
- 数据量特别大，内存无法容纳时
- 对容错性要求极高的场景
- 简单的批处理作业，不需要复杂的迭代计算
- 资源受限的环境

#### 问题3：在Spark中遇到数据倾斜如何定位和解决？

**我的回答**：
**定位方法**：
- 通过Spark UI观察任务执行时间差异
- 查看各个分区的数据量分布
- 分析业务数据特征，识别热点key

**解决方案**：
1. **预处理**：在数据源头进行预聚合
2. **加盐技术**：为倾斜的key添加随机前缀
3. **两阶段聚合**：先局部聚合，再全局聚合
4. **调整并行度**：增加分区数分散数据
5. **使用广播Join**：小表广播避免shuffle

**面试官追问**：如果是join操作导致的倾斜呢？

**我的回答**：
- 使用Map-side Join：将小表广播到各个节点
- 拆分倾斜key：将热点数据单独处理
- 加盐Join：对join key进行加盐处理

#### 编程题：用Spark SQL实现用户留存率计算

**题目要求**：给定用户行为表，计算7日留存率

**我的实现**：
```sql
WITH user_first_day AS (
  SELECT user_id, MIN(DATE(event_time)) as first_day
  FROM user_behavior 
  GROUP BY user_id
),
retention_analysis AS (
  SELECT 
    u.user_id,
    u.first_day,
    CASE WHEN b.user_id IS NOT NULL THEN 1 ELSE 0 END as day7_retained
  FROM user_first_day u
  LEFT JOIN (
    SELECT DISTINCT user_id, DATE(event_time) as event_date
    FROM user_behavior
  ) b ON u.user_id = b.user_id 
    AND b.event_date = DATE_ADD(u.first_day, 7)
)
SELECT 
  first_day,
  COUNT(*) as new_users,
  SUM(day7_retained) as retained_users,
  SUM(day7_retained) * 100.0 / COUNT(*) as retention_rate
FROM retention_analysis
GROUP BY first_day
ORDER BY first_day;
```

## 二面：系统设计面试（60分钟）

### 面试官背景
架构师，负责整体技术架构设计，有丰富的大数据平台建设经验。

### 系统设计题目

**题目**：设计一个实时推荐系统的数据处理架构，要求：
- 支持千万级用户
- 实时性要求在100ms内
- 支持A/B测试
- 具备容错和扩展能力

### 我的设计思路

#### 1. 整体架构
```
用户行为 -> Kafka -> Flink -> Redis/HBase -> 推荐服务
                  |
                  v
              离线训练 -> 模型更新
```

#### 2. 技术选型说明

**数据采集层**：
- Kafka：高吞吐量消息队列，支持数据回放
- 分区策略：按用户ID hash分区，保证同一用户数据有序

**实时计算层**：
- Flink：低延迟流处理，支持复杂事件处理
- 窗口策略：滑动窗口计算用户实时特征
- 状态管理：使用RocksDB存储用户历史行为

**存储层**：
- Redis：热数据缓存，毫秒级响应
- HBase：海量数据存储，支持随机读写
- HDFS：离线数据存储，支持模型训练

**服务层**：
- 推荐服务：基于实时特征和模型进行推荐
- A/B测试：流量分割和效果对比

#### 3. 关键技术点

**数据分区策略**：
```java
// 按用户ID hash分区
public class UserPartitioner implements Partitioner {
    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                        Object value, byte[] valueBytes, Cluster cluster) {
        return Math.abs(key.hashCode()) % cluster.partitionCountForTopic(topic);
    }
}
```

**缓存策略**：
- L1缓存：本地缓存热点用户数据
- L2缓存：Redis集群缓存用户特征
- L3缓存：HBase存储全量用户数据

**容错机制**：
- Flink checkpoint保证exactly-once语义
- Kafka offset管理支持故障恢复
- 多副本存储保证数据可靠性

**扩展性设计**：
- 水平扩展：增加Kafka分区和Flink并行度
- 垂直扩展：优化算法和数据结构
- 动态调整：根据负载自动扩缩容

### 项目经验深挖

- 业务场景多样：实时监控、实时推荐、实时风控等

#### 2. 技术难点攻坚

**问题**：项目中遇到的最大技术挑战是什么？

**我的回答**：
最大的挑战是Flink状态管理导致的内存溢出问题。

**问题现象**：
- Flink任务运行一段时间后出现OOM
- 状态大小持续增长，无法回收
- 影响系统稳定性和数据处理时效

**问题定位过程**：
1. **监控分析**：通过Flink Web UI观察状态大小变化
2. **代码审查**：检查状态使用逻辑，发现状态清理不及时
3. **压测验证**：模拟生产环境数据量进行压力测试
4. **内存分析**：使用JProfiler分析内存使用情况

**解决方案**：
1. **状态TTL设置**：为状态设置合理的过期时间
```java
StateTtlConfig ttlConfig = StateTtlConfig
    .newBuilder(Time.hours(24))
    .setUpdateType(StateTtlConfig.UpdateType.OnCreateAndWrite)
    .setStateVisibility(StateTtlConfig.StateVisibility.NeverReturnExpired)
    .build();

ValueStateDescriptor<String> descriptor = new ValueStateDescriptor<>("state", String.class);
descriptor.enableTimeToLive(ttlConfig);
```

2. **状态后端优化**：使用RocksDB状态后端，启用增量checkpoint
3. **内存配置调优**：合理分配TaskManager内存
4. **业务逻辑优化**：减少不必要的状态存储

**效果验证**：
- 内存使用量降低60%
- 任务稳定运行超过30天无重启
- 处理延迟从分钟级优化到秒级

#### 3. 性能优化经验

**问题**：如何将数据处理延迟从秒级优化到毫秒级？

**我的回答**：
从多个维度进行了系统性优化：

**代码层面优化**：
1. **算法优化**：使用更高效的数据结构和算法
2. **序列化优化**：使用Kryo序列化替代Java序列化
3. **对象复用**：减少对象创建和GC压力

**配置层面优化**：
1. **并行度调整**：根据数据量和资源情况调整并行度
2. **内存分配**：优化TaskManager和JobManager内存配置
3. **网络配置**：调整网络缓冲区大小

**架构层面优化**：
1. **缓存策略**：引入多级缓存减少计算量
2. **数据预处理**：在数据源头进行预聚合
3. **异步处理**：使用异步I/O提高吞吐量

**具体配置示例**：
```yaml
taskmanager:
  memory:
    process.size: 4gb
    flink.size: 3.2gb
    managed.fraction: 0.4
  numberOfTaskSlots: 4
  
parallelism.default: 16

state.backend: rocksdb
state.backend.incremental: true
state.checkpoints.dir: hdfs://namenode/checkpoints
```

#### 4. 团队协作

**问题**：如何与其他团队协作？遇到分歧如何处理？

**我的回答**：
在项目中需要与多个团队协作，包括业务团队、运维团队、测试团队等。

**协作经验**：

**分歧处理案例**：

2. **技术调研**：调研业界最佳实践，评估技术可行性

**问题**：对于流批一体化，你有什么看法？

**技术层面**：

- Spark Structured Streaming统一流批API
- Delta Lake、Iceberg等存储格式支持流批读写

**业务价值**：

**实践建议**：
